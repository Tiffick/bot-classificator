WHY THIS STAGE WAS NEEDED
-------------------------

Behavioral live testing exposed two technical contract failures.

1. LOCAL ID NAMESPACES

The LLM returned local identifiers such as:

ac1
rt_local_1

instead of the required contract namespaces:

item:
relation:
content:
target:
segment:

The prompt previously listed the namespaces but did not explicitly map every
field to its required namespace or prohibit aliases.

The Cognitive Core prompt was hardened so every local ID type has an explicit
namespace and all references must reuse the exact declared local ID.

This was independently audited against ai/cognitive_turn.py and accepted.


2. SOURCE SPAN OWNERSHIP

During the third behavioral turn the LLM repeatedly returned:

source_span = [0, 53)

for a USER message whose exact length was 52 characters.

This happened again even after the prompt explicitly instructed the model to
respect exact character offsets.

This demonstrated that exact character coordinate calculation is the wrong
responsibility for the LLM.

Architectural ownership was corrected:

LLM
    selects semantic evidence as an exact verbatim source_quote

Python
    deterministically converts source_quote into SourceSpan

The internal CognitiveTurnResult contract still uses numeric SourceSpan.
StateApplier and the persistent Data Model remain unchanged.


SOURCE_QUOTE EVIDENCE BOUNDARY
------------------------------

The API-facing Cognitive Core schema now uses source_quote instead of numeric
source_span in all three evidence paths:

- ItemOperation evidence
- RelationOperation evidence
- reconciliation evidence

The LLM must return an exact verbatim substring from the CURRENT USER message.

Python then:

1. verifies that the quote is non-empty where required;
2. searches the unchanged USER message for all exact occurrences;
3. accepts only one unique exact occurrence;
4. computes:

   char_start = exact occurrence position
   char_end   = char_start + len(source_quote)

5. creates the ordinary internal SourceSpan;
6. validates the resulting CognitiveTurnResult;
7. performs the existing numeric boundary validation.

No fuzzy matching is used.

No lowercase conversion, whitespace normalization, Unicode normalization,
punctuation repair or other heuristic correction is used.

If the quote:

- is missing when required;
- is empty;
- does not exist in the USER message;
- occurs more than once;

the Cognitive Core fails with:

CognitiveCoreError(category="validation_failure")

Python does not choose the first duplicate occurrence.

Overlapping duplicate occurrences are also detected.

There is no retry and no fallback.


DEFENSIVE VALIDATION
--------------------

The previous numeric SourceSpan boundary validation remains in CognitiveCore.

For every resulting SourceSpan:

0 <= char_start < char_end <= len(current_user_message.text)

StateApplier keeps its own defensive validation.

Persistent SourceReference validation also remains unchanged.

Therefore the new source_quote adapter does not replace existing protections;
it adds a deterministic evidence boundary before persistence.

DISCOVERY — MECHANISM / EXPERTISE FUNCTION RESTORED
================================================================================

STATUS
------

Architecture clarification complete.

Research source of truth updated and committed:

    9142a7c Clarify Discovery expertise and sufficiency

Commit pushed to main.

This is NOT a new product direction.

It restores an important function of Discovery that existed in the intended
consultation model but had been underrepresented during formalization of the
Cognitive Cycle and Product Boundary.


WHAT WAS MISSING
----------------

During behavioral evaluation of the first Cognitive Core turns, Discovery was
being evaluated too strongly through one major product function:

    HUMAN / MEANINGFUL CHANGE

That function answers questions such as:

    What has the problem changed in this person's life?
    What does it mean to this person?
    What does the person want to regain or change?

Desired user effect:

    "Меня действительно поняли."

This remains essential.

However, Previous Attempts / Barriers have another independent product function
that must also be preserved:

    MECHANISM / EXPERTISE

The consultation should be capable of understanding enough of the person's
experienced problem mechanism to create a justified sense that the situation
is professionally recognizable.

Desired user effect:

    "Знакомо.
     Они понимают, что со мной происходит.
     Они понимают, почему мои предыдущие попытки не сработали.
     Похоже, они знают, как с такими ситуациями работать."

Compact internal formulation:

    "Знаем это. Знаем почему. Знаем как решить."

This does NOT authorize the AI to pretend certainty or knowledge that has not
actually been established.


TWO COMPLEMENTARY DISCOVERY LINES
---------------------------------

Discovery now explicitly recognizes at least two complementary lines of useful
understanding.

LINE A — HUMAN / MEANINGFUL CHANGE

May include:

    experience
    Before -> Now
    life changes
    limitations
    adaptations
    Personal Meaning
    Desired Change / Return

Primary product value:

    understand the person and what the problem has changed for them.


LINE B — MECHANISM / EXPERTISE

May include:

    Previous Attempts
    why an attempt was not sustainable in the user's experience
    substantial Barriers
    recurring mechanisms or patterns
    discriminating between materially different working explanations

Primary product value:

    understand the problem well enough for professional recognition.

Neither line is a required stage.

There is no mandatory order:

    A -> B

or:

    B -> A

There is no requirement for equal depth in every conversation.

Cognitive Core must compare the expected value of available Decisions in the
specific conversation.


EPISTEMIC BOUNDARY
------------------

Expert Recognition is NOT Objective Diagnosis.

The user's subjective experience is sufficient for a working model.

The system may understand and test working explanations without claiming that
it has established an objective physiological, psychological, behavioral, or
medical cause.

A hypothesis remains a hypothesis.

A user-supported interpretation remains provenance-aware.

Expertise must not be simulated by artificial certainty.


VALUE / SUFFICIENCY CLARIFICATION
---------------------------------

The previous practical question:

    "Will this answer teach us something new?"

is too weak.

Almost any additional question can produce new information.

The opposite restriction:

    "Is this information needed for Meaningful Change Picture?"

is also too narrow.

A question can have legitimate value because it materially improves
Mechanism / Expertise understanding.

The broader criterion is:

    Will the next answer materially improve useful understanding of the person
    OR a substantial mechanism of the person's problem within the current
    product boundary?

A branch should stop when further detail has low expected value for current
Discovery compared with another available Decision.

Further detail must not be collected merely because it could be useful to a
future specialist or future solution design.


BOUNDARY WITH SOLUTION DESIGN
-----------------------------

Useful Mechanism / Expertise exploration may:

    distinguish materially different working explanations;
    clarify why a previous attempt was not sustainable;
    identify a substantial recurring Barrier;
    improve the accuracy of Reflection;
    improve the next Discovery Decision;
    create justified professional recognition.

It becomes excessive diagnostic exploration when additional detail:

    barely changes the working Formulation;
    is collected mainly to select or tune a future solution;
    attempts to establish an objective medical / physiological /
    psychological cause;
    continues an already sufficient branch merely because more information
    can be obtained;
    has lower expected value than another useful Discovery Decision.

The boundary is semantic and value-based.

It is NOT defined by keywords, a fixed number of questions, required fields,
or a hardcoded route.

COGNITIVE CORE — MINIMAL DECISION CONTRACT
================================================================================

После полного Conversation Lab и последующего offline architecture audit
было установлено, что Value / Sufficiency и Product Boundary существовали
в runtime прежде всего как инструкции Cognitive LLM, но выбранный Decision
не имел явного представления в CognitiveTurnResult.

До изменения runtime имел вид:

INPUT
→ one Cognitive LLM call
→ CognitiveTurnResult {
    state_patch,
    reconciliation,
    system_action,
    reply_segments
  }
→ DiscoveryStateApplier.

Из system_action можно было лишь косвенно восстанавливать выбранное действие.
Python не имел явной информации о том, продолжает ли Core Human Discovery,
Mechanism Discovery, делает Reflection, Recognition, Transition,
уважает отказ, завершает Discovery или отвечает на прямой вопрос.

Принято архитектурное решение:
Decision должен стать минимальной ephemeral частью CognitiveTurnResult,
не создавая отдельного DecisionEngine и не сохраняя reasoning.

Добавлен обязательный DecisionIntent:

- HUMAN_DISCOVERY
- MECHANISM_DISCOVERY
- REFLECTION
- RECOGNITION
- TRANSITION
- RESPECT_PAUSE_OR_REFUSAL
- STOP_EXPLORATION
- ANSWER_USER_QUESTION

Добавлено обязательное поле:

CognitiveTurnResult.decision_intent

DecisionIntent:
- создаётся тем же единственным Cognitive LLM call;
- выбирается до Response;
- описывает функцию выбранного действия Cognitive Cycle, а не тему текста;
- ephemeral;
- не сохраняется в HumanModel;
- не сохраняется в ACS;
- не сохраняется в DialogueHistory;

- REFLECTION требует SYSTEM_REFLECTION;

- RESPECT_PAUSE_OR_REFUSAL не открывает новый OPEN_RESPONSE/CLARIFICATION;
- CONSENT может адресовать только SYSTEM_PROPOSAL или SYSTEM_TRANSITION;
- SYSTEM_REFLECTION не может быть предметом CONSENT;
- корректный owner/subject lifecycle из предыдущего hardening сохранён.

Сознательно НЕ реализованы:

- semantic Product Boundary classifier;
- keyword/phrase matching;
- Python-интерпретация semantic_content;

вынести человеку рабочую версию и попросить её подтвердить, отвергнуть
или исправить?

Была сформулирована альтернативная стратегия:

TESTABLE WORKING VERSION.

Пример функции:

"Похоже, здесь могли действовать разные вещи.
Это только рабочие версии, не установленные причины.
На ваш опыт это похоже, частично похоже или было иначе?"

Ключевая идея:

неопределённость системы сама по себе не является причиной задавать
дополнительный вопрос.

Если grounded working version уже можно безопасно вынести пользователю,
Evaluation этой версии сама может дать полезный Human Model delta.

Возможные результаты:

SUPPORTED
REJECTED
PARTIALLY_SUPPORTED
UNCERTAIN
user correction

Все они являются полноценным Discovery result.


ARCHITECTURE AUDIT OF TESTABLE WORKING VERSION
----------------------------------------------

Offline audit подтвердил, что новая сущность или новый intent не нужны.

Существующая архитектура уже поддерживает этот путь через:

RECOGNITION
+
RECOGNITION_OPTION
+
EVALUATION
+
ProposalMaterialization
+
SYSTEM_PROPOSED provenance.

REFLECTION также может использоваться, если осторожная версия встроена
в более широкую working picture.

Expert Recognition остаётся:

NOT Objective Diagnosis.

Working version:

- не становится фактом;
- сохраняет provenance;
- может быть отвергнута;
- может быть частично поддержана;
- может остаться uncertain;
- может быть исправлена пользователем.

Human Experience по-прежнему:

NOT evidence о конкретном пользователе.


DIRECT DISCRIMINATION VS TESTABLE WORKING VERSION
-------------------------------------------------

Был подготовлен отдельный frozen product-policy A/B experiment.

A — DIRECT DISCRIMINATION

Вопрос запрашивает доступное пользователю наблюдение,
которое может различить materially different working explanations.

B — TESTABLE WORKING VERSION

Уже имеющийся пользовательский материал используется для осторожной,
явно гипотетической working version, после чего пользователь оценивает её.

Для эксперимента была создана новая симметричная product rubric.

Она сравнивала:

- Expected Human Model delta;
- User burden;
- Grounding;
- Correctability;
- Epistemic safety;
- Forward value;
- Natural consultation quality;
- Product Boundary.

Критическое правило rubric:

REDUCTION OF SYSTEM UNCERTAINTY
не имеет самостоятельной пользовательской ценности.

Ни A, ни B не получают преимущества по типу действия.

REVISED VALUE PRINCIPLE
-----------------------

Принято новое value-based правило:

REDUCTION OF SYSTEM UNCERTAINTY
САМА ПО СЕБЕ
НЕ ЯВЛЯЕТСЯ ПОЛЬЗОВАТЕЛЬСКОЙ ЦЕННОСТЬЮ.

Если уже имеющийся пользовательский материал позволяет сформулировать:

- grounded;
- безопасную;
- легко отвергаемую;
- provenance-aware

TESTABLE WORKING VERSION,

и Evaluation этой версии способна существенно улучшить:

- Human Model;
- Formulation;
- или следующий полезный Decision,

дополнительный epistemic question НЕ ОБЯЗАТЕЛЕН.

DIRECT DISCRIMINATION сохраняет полноценную роль.

Она предпочтительна, когда доступное пользователю различающее наблюдение
даёт больший expected useful delta для:

- Formulation;
- различения materially different working explanations;
- следующего полезного Decision.

Таким образом правило НЕ является:

"Recognition лучше вопроса."

И НЕ является:

"Не задавать уточняющих вопросов."

Правило является:

сравнивать ожидаемую ПОЛЕЗНУЮ ценность действий,
а не количество неопределённости, которое Core сможет убрать.


GUARDS
------

Testable Working Version допустима только при сохранении границ:

- grounded в пользовательском материале;
- hypothesis != fact;
- system-proposed provenance;
- Human Experience != evidence;
- пользователь может подтвердить;
- частично подтвердить;
- отвергнуть;
- исправить;
- сказать "не знаю";
- никакого objective medical / physiological / psychological diagnosis;
- никакой generic ungrounded causal guess;
- никакой ritual Reflection;
- rejected version не возвращается автоматически без нового основания;
- Recognition не используется для продавливания согласия;
- дополнительная деталь не собирается только ради уверенности Core.

КОНТЕКСТ

работа продолжилась над фактическим поведением Cognitive Core и границей
ответственности между Cognitive LLM и deterministic Python layer.

К этому моменту production architecture сохраняла:

    ONE COGNITIVE LLM CALL
    +

    +

Однако последующий behavioral analysis показал две связанные проблемы:

1. Decision Policy стала чрезмерно операционализированной и заставляла модель
   выполнять искусственную процедуру выбора вместо естественного
   консультативного мышления.

2. Один Cognitive LLM call одновременно отвечал и за человеческий смысл
   следующего хода, и за значительный объём технической упаковки
   CognitiveTurnResult.

Этот этап был посвящён упрощению обеих границ без создания нового Engine,
второго LLM call или нового persistent state.


================================================================================
I. SIMPLIFICATION OF CONSULTANT POLICY
================================================================================

Предыдущая Operational Decision Policy требовала от Cognitive Core
внутренне выполнять развитый candidate-selection protocol, включавший:

- candidate generation;
- response forecasting;
- decision hinge;
- strongest alternative;
- Direct-vs-Working-Version comparison;
- winner commitment.

Эта конструкция появилась как попытка сделать Value / Sufficiency
и выбор следующего Decision более надёжными.

Дальнейший анализ показал, что система стала слишком сильно оптимизироваться
под эпистемическую точность и формальный выбор действия.

Для естественной консультации это неверная цель.

Ключевой продуктовый вывод:

    хороший консультант не обязан исчерпывать неопределённость
    перед каждым следующим ходом.

Допустимы grounded, low-cost, reversible assumptions.

Если такая рабочая версия немного неточна, пользователь может её поправить.
Исправление пользователя является нормальной частью разговора,
а не failure системы.


SIMPLIFIED CONSULTANT POLICY
----------------------------

Операционная policy была сведена к более естественным принципам:

1. Сначала понять / принять.

   Использовать уже сказанный пользователем материал и не требовать
   дополнительного подтверждения ясных фактов только потому,
   что теоретически возможна другая интерпретация.

2. Не уточнять без необходимости.

   Clarification оправдан только тогда, когда существуют materially different
   plausible interpretations смысла пользователя и выбор между ними
   существенно меняет следующий полезный ход.

3. Исследовать patterns, а не устраивать causal autopsy каждого episode.

   Один отдельный эпизод сам по себе не требует подробного поиска причин.

   Повторяющийся или центральный pattern может оправдывать
   Mechanism / Expertise exploration.

4. Reflection использовать только тогда, когда она добавляет synthesis,
   working picture или новое понимание.

   Простое повторение последней пользовательской реплики не является
   достаточной причиной для Reflection.

5. Уметь двигаться дальше.

   Возможность получить ещё одну деталь не означает,
   что эту деталь нужно обязательно получать.

Итоговый ориентир:

    "Меня действительно поняли"

важнее, чем:

    "Меня идеально классифицировали."

Старая многоступенчатая candidate-selection machinery была удалена
из production policy.

DecisionIntent contract при этом не изменялся.

Selected-only boundary сохранена.


================================================================================
II. SEMANTIC / TECHNICAL RESPONSIBILITY BOUNDARY
================================================================================

Отдельный architecture audit показал,
что Cognitive LLM выполняла слишком много deterministic bookkeeping.

В одном structured output модель должна была одновременно:

- понять человека;
- интегрировать текущую реплику;
- выбрать semantic Decision;
- сформулировать SystemAction;
- определить state changes;
- создать technical local IDs;
- соблюдать namespaces;
- оформлять ownership;
- связывать targets и contents;
- связывать ReplySegments;
- оформлять references;
- соблюдать evidence representation;
- удовлетворять многочисленным cross-reference invariants.

Это создавало неправильную failure boundary:

    семантически хороший консультативный ход
    мог быть отвергнут из-за ошибки технической упаковки.

Принят архитектурный принцип:

    LLM decides WHAT the conversation means.

    Python decides HOW to technically record/package it.

При этом Python не получает права интерпретировать человеческий смысл.

Python не должен:

- угадывать semantic intent;
- классифицировать смысл по keywords;
- исправлять semantic decisions модели;
- выводить причинность;
- выбирать за LLM Human / Mechanism / Reflection / Transition;
- подменять semantic reasoning deterministic rules.

III. SEMANTIC TURN CONTRACT
================================================================================

Добавлен новый production module:

    ai/cognitive_semantic_wire.py

Он содержит SemanticTurn contract и deterministic adapter.

Новый Cognitive Core path:

    gpt-5-mini
    →
    SemanticTurn
    →
    deterministic Python adapter
    →
    CognitiveTurnResult

SemanticTurn выражает semantic result одного Cognitive LLM turn
без требования к модели выполнять лишний deterministic bookkeeping.


SEMANTIC RESPONSIBILITY
-----------------------

LLM по-прежнему определяет:

- state meaning;
- ADD / REINFORCE / CORRECT semantic operation;
- semantic referent;
- evidence fragment;
- reconciliation meaning;
- selected DecisionIntent;
- semantic ActionContent;
- ResponseTarget meaning;
- interaction semantics;
- user-facing response.


DETERMINISTIC RESPONSIBILITY
----------------------------

Python adapter выполняет техническую материализацию:

- назначает technical IDs;
- разрешает local handles;
- разворачивает references;
- создаёт operation fields;
- преобразует exact source_quote в SourceSpan;
- материализует reconciliation;
- материализует proposal references;
- создаёт content / target / segment IDs;
- собирает существующий CognitiveTurnResult;
- запускает его structural validation.

Adapter не выполняет semantic guessing.

Невалидный SemanticTurn по-прежнему обрабатывается fail closed.

V. META-CONVERSATION DEFECT
================================================================================

После первоначального упрощения policy был проведён live behavioral acceptance.

Он выявил систематический defect:

    META_CONVERSATION.

В нескольких сценариях Core начинал обсуждать с пользователем
сам процесс консультации:

    "Нужно ли вообще знать больше?"
    "Хотите, чтобы я уточнил подробнее?"
    "Нужно ли здесь продолжать разбираться?"

Root cause оказался локальным.

Внутренний decision criterion был сформулирован в policy слишком буквально
как инструкция сначала спросить, нужно ли знать больше.

Модель выполняла эту инструкцию как пользовательский вопрос.


АРХИТЕКТУРНОЕ УТОЧНЕНИЕ
-----------------------

Необходимость дополнительной информации является внутренним
Cognitive Decision.

Core должен сам решить:

    нужна ли ещё информация для следующего полезного хода?

Этот внутренний критерий не должен автоматически становиться
темой разговора с пользователем.

Production policy была уточнена:

- не озвучивать внутренний критерий необходимости информации;
- не предлагать пользователю выбирать режим
  "уточнять или продолжать";
- не обсуждать механику консультационного процесса,
  если она сама не является содержанием разговора.

Последующий live confirmation:

    META_CONVERSATION = PASS.

Старый systematic meta-pattern не воспроизвёлся.


================================================================================
VI. PRODUCT BOUNDARY — UNDERSTANDING VS PERSONAL SOLUTION DESIGN
================================================================================

Во время behavioral acceptance был уточнён фундаментальный Product Boundary.

Принято owner/product решение:

    AI помогает человеку глубоко понять его проблему,
    но НЕ проектирует персональное решение за него.

Discovery имеет самостоятельную пользовательскую ценность.

Его функция не сводится к сбору информации для будущего консультанта.


AI МОЖЕТ
--------

В текущем Discovery layer AI может:

- связывать известные факты;
- показывать patterns;
- помогать человеку увидеть,
  где именно возникает трудность;
- исследовать meaningful Previous Attempts / Barriers / Mechanisms;
- формировать grounded synthesis;
- давать Recognition;
- объяснять general mechanisms / principles,
  если это помогает пониманию;
- отвечать на прямые вопросы пользователя,
  пока ответ остаётся в understanding / problem framing.

Желаемый эффект:

    "Теперь я понимаю, где именно у меня ломается."


AI НЕ ДОЛЖЕН
------------

Текущий Discovery layer не должен:

- выбирать конкретную практику для пользователя;
- выбирать привычку;
- проектировать изменение окружения;
- создавать персональный if-then plan;
- составлять индивидуальный режим;
- назначать диету / калории;
- выбирать продукты или программу;
- превращать general principle в конкретный способ действий
  для данного пользователя;
- предлагать самому AI подобрать, адаптировать
  или разработать персональное решение.

Это:

    PERSONAL SOLUTION DESIGN.

Personal Solution Design относится к следующему human consultation layer.


================================================================================
VII. GENERAL EXPLANATION IS NOT PERSONAL SOLUTION DESIGN
================================================================================

Зафиксировано важное различие:

    GENERAL EXPLANATION
    !=
    PERSONAL SOLUTION DESIGN.

Прямой вопрос пользователя:

    "Что мне делать?"

или:

    "Как сделать так, чтобы результат не развалился?"

НЕ отменяет Product Boundary.

Он также НЕ создаёт автоматический Transition.

Cognitive Core сначала должен дать столько полезного понимания,
сколько естественно следует из уже известного материала пользователя.

Допустимо:

    "Похоже, у вас проблема действительно не в способности начать.
     Вы уже несколько раз показали, что начинать и получать результат можете.
     Сложность возникает позже — когда изменения должны превратиться
     из временного усилия в устойчивую часть жизни."

Это углубляет понимание проблемы,
но не проектирует персональное решение.

Если следующий полезный шаг уже требует:

- выбора конкретного подхода;
- адаптации метода;
- проектирования практики;
- построения персонального плана;

тогда это естественная граница для Transition
к живому консультанту с meaningful consent.

Transition определяется содержанием следующего полезного шага,
а не формой вопроса пользователя.

НОВЫЙ ENGINE НЕ НУЖЕН.

======================================================================
VI. PERSISTENCE AND ATOMICITY
======================================================================

Discovery persistence выполняется только после полного успешного:

CognitiveCore.propose()
→ SemanticTurn validation
→ deterministic adapter
→ CognitiveTurnResult
→ apply_cognitive_turn()

Только после этого одной заменой сохраняются:

- updated HumanModel;
- new ActiveConversationState;
- updated DialogueHistory.

При CognitiveCore failure:

- persistent Discovery memory не меняется;
- USER message отдельно не сохраняется;
- fallback LLM не запускается.

При StateApplier failure:

- partial HumanModel не сохраняется;
- ACS не сохраняется;
- partial DialogueHistory не сохраняется.

Это сохраняет atomic turn semantics:

либо весь когнитивный ход принят и сохранён,
либо persistent state остаётся прежним.

персональные варианты.

Это нарушало уже принятую Product Boundary:

    AI помогает человеку глубоко понять его проблему,
    но не проектирует персональное решение за него.

VIII. BOOKKEEPING LEAK AUDIT
===============================================================================

Read-only architecture audit подтвердил:

    это небольшой оставшийся deterministic bookkeeping leak
    в SemanticTurn contract.

Принцип архитектуры:

    LLM decides WHAT the conversation means.
    Python decides HOW to technically record/package it.

был ещё не полностью реализован
для reconciliation previous ResponseTargets.

LLM получала одновременно:

- ActiveContent persistent ID;
- ResponseTarget persistent ID;
- ownership;
- subject;
- interaction;

и должна была правильно скопировать технический rt_* ID.

В singleton target state это не требовало semantic reasoning.

Также был обнаружен redundant API-facing field:

    previous_active_content_id

поскольку выбранный ResponseTarget уже однозначно определяет
связанный ActiveContent.


===============================================================================
IX. SEMANTIC TARGET REFERENCE CLEANUP
===============================================================================

SemanticTurn был узко очищен.

API-facing contract изменён:

BEFORE:

    reconciliation.previous_target_ids

AFTER:

    reconciliation.previous_target_handles

BEFORE:

    resolution_target_id

AFTER:

    resolution_target_handle

API-facing:

    previous_active_content_id

удалён.

Previous ResponseTargets теперь проецируются модели
через input-scoped semantic handles:

    previous_target_1
    previous_target_2
    ...

LLM определяет:

    КАКУЮ semantic target пользователь адресовал.

Python deterministic adapter определяет:

    какой persistent rt_* соответствует этому handle.

Для materialization используется тот же принцип.

Связанный previous ActiveContent выводится Python
механически из выбранного ResponseTarget.

При нескольких previous targets:

- LLM выбирает semantic target handle;
- Python делает handle → persistent ID resolution;
- Python не интерпретирует русский пользовательский текст.

РЕАЛИЗОВАННЫЕ ИЗМЕНЕНИЯ

1. Decision policy

В production prompt введён принцип достаточного понимания.

Если повторяющийся механизм, его значение для человека
и последствия уже достаточно обоснованы контекстом,
дальнейшее уточнение предпочтительно только тогда,
когда ответ способен существенно изменить рабочее понимание
или следующий выбор действия.

Иначе предпочтительны:
- содержательная REFLECTION;
- обоснованная RECOGNITION;
- уместное продвижение разговора.

Правило не является квотой вопросов или требованием выполнять
REFLECTION после определённого количества сообщений.

Сохраняется гибкость Cognitive Core.


2. Response composition

Принцип anti-echo распространён на все DecisionIntent.

Ответ не должен механически повторять очевидное утверждение
пользователя, если повторение не добавляет связи,
следствия или нового понимания.

Эмоциональная чувствительность темы сама по себе
не оправдывает повторяющиеся вступления
«Понял», «Спасибо» и аналогичные формулы.


3. Question burden

Установлен приоритет одного основного разговорного запроса
на один ход.

Допускаются естественные составные вопросы, если они
обслуживают одну когнитивную задачу.

Несколько независимых уточнений не должны превращать
ответ в анкету.


4. Документация

Соответствующие правила синхронизированы с authoritative
Research/Human_Experience/Weight/12_Cognitive_Cycle.txt.

Сохранено разграничение:
- обоснованное понимание;
- рабочая гипотеза;
- недопустимое представление предположений как фактов.
