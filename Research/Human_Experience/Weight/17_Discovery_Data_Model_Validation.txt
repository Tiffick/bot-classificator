DISCOVERY DATA MODEL — ADVERSARIAL VALIDATION

Статус документа:
Проверка логической модели Discovery Data Model
на сценариях, которые могут разрушить её архитектурные предположения.

Основа проверки:
12_Cognitive_Cycle.txt
13_Active_Conversation_State.txt
14_Human_Model.txt
15_Discovery_Memory.txt
16_Discovery_Data_Model.txt

Цель:
до создания технической схемы проверить,
достаточны ли:

MODEL ITEMS
+
RELATIONS
+
ACTIVE CONTENT
+
RESPONSE TARGET
+
DIALOGUE HISTORY

для разных форм естественного Discovery-разговора.


============================================================
1. ПОЛЬЗОВАТЕЛЬ СООБЩАЕТ НЕСКОЛЬКО ИЗМЕНЕНИЙ СРАЗУ
============================================================

Пример:

"Раньше фотографировался постоянно,
сейчас не хочется.
И перед женой футболку стараюсь не снимать."

Требуется сохранить:

MODEL ITEM:
раньше любил фотографироваться
KIND = BEFORE
PROVENANCE = USER PROVIDED

MODEL ITEM:
сейчас не хочется фотографироваться
KIND = NOW / LIFE CHANGE
PROVENANCE = USER PROVIDED

RELATION:
BEFORE → NOW

MODEL ITEM:
раньше спокойно находился раздетым перед женой
KIND = BEFORE
PROVENANCE = USER PROVIDED

MODEL ITEM:
сейчас старается не снимать футболку перед женой
KIND = NOW / LIFE CHANGE
PROVENANCE = USER PROVIDED

RELATION:
BEFORE → NOW

Результат:

Модель выдерживает сценарий.
Не требуется отдельный слот "photos" или "intimacy".


============================================================
2. ПОЛЬЗОВАТЕЛЬ САМ ПРЕДЛАГАЕТ ОБЪЯСНЕНИЕ
============================================================

Пример:

"Но это, наверное, просто возраст."

Требуется сохранить:

MODEL ITEM:
пользователь предполагает,
что описанные изменения могут быть связаны с возрастом

KIND = USER INTERPRETATION
PROVENANCE = USER INTERPRETATION

RELATION:
интерпретация относится к соответствующим изменениям

Важно:

Human Model не превращает это в:

"возраст вызвал изменения"

Результат:

Модель выдерживает сценарий.


============================================================
3. СИСТЕМА ПРЕДЛАГАЕТ ВЕРСИЮ — ПОЛЬЗОВАТЕЛЬ СОГЛАСЕН
============================================================

Система:

"Похоже, дело не только во внешности,
а ещё в том, что рядом с женой стало сложнее
чувствовать себя свободно. Так?"

Пользователь:

"Да, именно."

До ответа пользователя:

ACTIVE CONTENT:
предложенная системой связь между изменением тела
и снижением свободы рядом с женой

RESPONSE TARGET:
эта конкретная связь

После Integration:

RELATION / MODEL ITEM
PROVENANCE = SYSTEM PROPOSED
STATUS = SUPPORTED

Результат:

Модель выдерживает сценарий.


============================================================
4. СИСТЕМА ПРЕДЛАГАЕТ ВЕРСИЮ — ПОЛЬЗОВАТЕЛЬ ОТВЕРГАЕТ
============================================================

Пользователь:

"Нет, вообще не про это."

Требуется:

связать ответ с RESPONSE TARGET;

сохранить смысл проверенной версии:

PROVENANCE = SYSTEM PROPOSED
STATUS = REJECTED

Не добавлять предложенный смысл
как пользовательский факт.

Decision в будущем должен видеть,
что версия уже отвергнута.

Результат:

Модель выдерживает сценарий.


============================================================
5. НЕОДНОЗНАЧНЫЙ КОРОТКИЙ ОТВЕТ
============================================================

Пользователь:

"Может быть."

ACTIVE CONVERSATION STATE определяет,
к какой версии относится ответ.

Но текст не определяет
точную степень согласия.

После Integration:

STATUS = UNCERTAIN

Не требуется:

SUPPORTED
или
REJECTED

Decision решает,
нужно ли уточнение.

Результат:

Модель выдерживает сценарий.


============================================================
6. ЧАСТИЧНОЕ СОГЛАСИЕ С REFLECTION
============================================================

Система отражает картину из трёх элементов:

A
B
C

Пользователь:

"В целом да, но с женой не совсем так."

Новая реплика одновременно:

поддерживает часть Reflection;

корректирует конкретный элемент или связь.

Требуется:

не назначать один STATUS всей Reflection;

разрешить обновление отдельных MODEL ITEMS / RELATIONS;

сохранить пользовательскую коррекцию.

Вывод:

ACTIVE CONTENT не должен быть неделимым текстовым блоком.

Он должен позволять ссылаться
на отдельные смысловые элементы внутри ответа системы.

Результат:

Модель выдерживает сценарий
ПРИ УСЛОВИИ адресуемости элементов Active Content.


============================================================
7. RECOGNITION С НЕСКОЛЬКИМИ ВАРИАНТАМИ
============================================================

Система:

"У кого-то это проявляется так:
не хочется фотографироваться,
сложнее раздеваться перед партнёром
или начинаешь избегать каких-то активностей.
У тебя что-то из этого есть?"

Пользователь:

"Фото — да. Остальное нет."

Требуется независимо разрешить:

вариант 1 → SUPPORTED

вариант 2 → REJECTED

вариант 3 → REJECTED

Один общий RESPONSE TARGET недостаточен,
если он представляет весь Recognition
как неделимую единицу.

Вывод:

RESPONSE TARGET должен поддерживать
ОДИН ИЛИ НЕСКОЛЬКО адресуемых targets.

Результат:

Модель выдерживает сценарий
при уточнении контракта:

RESPONSE TARGET
может быть множественным.


============================================================
8. ПОЛЬЗОВАТЕЛЬ ОТВЕЧАЕТ И ДОБАВЛЯЕТ НОВЫЙ МАТЕРИАЛ
============================================================

Система задаёт вопрос о фотографиях.

Пользователь:

"Да, фотографироваться не люблю.
И вообще заметил, что на пляж уже второй год
не хочется ездить."

Integration должен сделать две разные операции:

1. разрешить RESPONSE TARGET;

2. добавить новый USER PROVIDED материал,
которого не было в Active Conversation State.

Perception не должен считать всю реплику
только ответом на предыдущий вопрос.

Результат:

Модель выдерживает сценарий.


============================================================
9. ПОЛЬЗОВАТЕЛЬ ИГНОРИРУЕТ ВОПРОС И МЕНЯЕТ ТЕМУ
============================================================

Система спрашивает:

"Хотел бы снова спокойно фотографироваться?"

Пользователь:

"Кстати, я уже несколько раз пытался худеть."

Новая реплика не разрешает RESPONSE TARGET.

Она вводит новый материал:

KIND = PREVIOUS ATTEMPT
PROVENANCE = USER PROVIDED

Предыдущий RESPONSE TARGET
не должен заставлять систему
трактовать реплику как ответ на вопрос.

Вывод:

Integration должен уметь определить:

TARGET NOT ANSWERED

без принуждения пользователя
вернуться к предыдущему вопросу.

Результат:

Модель выдерживает сценарий.


============================================================
10. ПОЛЬЗОВАТЕЛЬ ОТВЕЧАЕТ ВОПРОСОМ
============================================================

Система:

"Тебе хотелось бы вернуть это ощущение свободы?"

Пользователь:

"А это вообще реально?"

Новая реплика:

не является подтверждением или отрицанием;

является прямым вопросом пользователя;

семантически связана с Active Content.

Decision должен выбрать:

ANSWER USER QUESTION

а не продолжать извлечение ответа.

Результат:

Модель выдерживает сценарий.


============================================================
11. КОРРЕКЦИЯ РАНЕЕ ПОДДЕРЖАННОЙ ВЕРСИИ
============================================================

Ранее:

SYSTEM PROPOSED
"стыд перед женой"

STATUS = SUPPORTED

Позже пользователь говорит:

"Я неправильно сказал. Не стыд.
Скорее просто некомфортно."

Требуется:

старый элемент:
STATUS = CORRECTED / SUPERSEDED

новый элемент:
"некомфортно перед женой"
PROVENANCE = USER PROVIDED / USER CORRECTION

связь:
новый элемент заменяет старую рабочую версию

Результат:

Модель выдерживает сценарий,
если техническая схема поддерживает supersession.


============================================================
12. ПОЛЬЗОВАТЕЛЬ ВОЗВРАЩАЕТСЯ К СТАРОЙ ТЕМЕ
============================================================

Несколько ходов назад обсуждались фотографии.

Текущий Active Conversation State
относится к попыткам похудения.

Пользователь:

"Кстати, про фотографии.
Я понял, что на самом деле избегаю их
только когда видно живот."

Текущий ACS не содержит старую тему.

Но Human Model содержит элементы,
относящиеся к фотографиям,
а Dialogue History содержит исходный разговор.

Новая реплика достаточно явно
возвращается к существующему материалу.

Integration может обновить соответствующие MODEL ITEMS / RELATIONS.

Результат:

Модель выдерживает сценарий.

ACS не должен хранить все старые открытые темы.


============================================================
13. НЕЯВНАЯ ССЫЛКА НА БОЛЕЕ СТАРУЮ ВЕРСИЮ
============================================================

Пользователь:

"Нет, я всё-таки думаю, ты тогда был прав."

Если "тогда" относится не к последнему действию системы,
текущий ACS может быть недостаточен.

Dialogue History содержит старые системные версии.

Human Model может содержать значимые
SYSTEM PROPOSED элементы и их статусы.

Для надёжной интеграции может потребоваться
поиск референта среди Human Model
и ближайшей Dialogue History.

Вывод:

ACS остаётся состоянием последнего хода.

Не нужно превращать его
в список всех незавершённых прошлых предложений.

Результат:

Модель выдерживает сценарий
за счёт Human Model + Dialogue History.


============================================================
14. НЕСКОЛЬКО НЕРАЗРЕШЁННЫХ ВЕРСИЙ ЧЕРЕЗ НЕСКОЛЬКО ХОДОВ
============================================================

Если система последовательно предлагает
несколько версий,
а пользователь не отвечает на них напрямую,
они не должны бесконечно оставаться
"активными" в ACS.

Если версия достаточно значима,
чтобы влиять на будущий Decision,
она может существовать в Human Model как:

SYSTEM PROPOSED
STATUS = UNCERTAIN

Если она была лишь временным вопросом
и пользователь её не поддержал,
она может не становиться устойчивым
элементом Human Model.

Вывод:

ACS не является backlog гипотез.

Результат:

Модель выдерживает сценарий.


============================================================
15. ДРУГОЙ ЧЕЛОВЕК В РАССКАЗЕ
============================================================

Пользователь:

"Жена говорит, что я нормально выгляжу."

Требуется сохранить:

CONTENT:
жена говорит, что пользователь нормально выглядит

KIND = OTHER PERSON VIEW
PROVENANCE = OTHER PERSON

Нельзя автоматически вывести:

пользователь доволен внешностью;

пользователь верит жене;

проблема незначима;

мотивация снизилась.

Результат:

Модель выдерживает сценарий.


============================================================
16. ОДНА РЕПЛИКА СОДЕРЖИТ ПРОТИВОРЕЧИВОЕ ПЕРЕЖИВАНИЕ
============================================================

Пользователь:

"Мне вроде всё равно,
но когда вижу себя на фото — бесит."

Не требуется выбирать
одну "истинную" версию.

Human Model может содержать
оба пользовательских элемента.

Formulation определяет,
как они сосуществуют
и нужно ли уточнение.

Data Model не должен автоматически
считать это техническим contradiction error.

Результат:

Модель выдерживает сценарий.


============================================================
17. ПЕРСОНАЛЬНАЯ ЗНАЧИМОСТЬ НЕ УСТАНОВЛЕНА
============================================================

Пользователь сообщил Life Change:

"Перестал фотографироваться."

Но не сказал,
важно ли ему это.

Human Model сохраняет Life Change.

Personal Meaning не создаётся автоматически.

Decision может:

- исследовать значимость;
- не исследовать её,
  если она не нужна для следующего полезного шага.

Результат:

Модель выдерживает сценарий.


============================================================
18. ПОЛЬЗОВАТЕЛЬ НЕ ХОЧЕТ ПРОДОЛЖАТЬ ТЕМУ
============================================================

Пользователь:

"Не хочу сейчас про это."

Это самостоятельный пользовательский материал
для текущего Decision.

Система должна:

Respect Pause / Refusal

и не продолжать Recognition
или Deepen Current Area
только потому, что RESPONSE TARGET
остался неразрешённым.

Не каждый незакрытый target
должен быть закрыт.

Результат:

Модель выдерживает сценарий.


============================================================
19. TRANSITION
============================================================

Система предлагает:

"Если хочешь, дальше это уже можно разобрать
с живым консультантом."

ACTIVE CONTENT:
конкретное предложение следующего шага

RESPONSE TARGET:
согласие / отказ / вопрос / неопределённость
относительно этого предложения

Пользователь:

"Да, давай."

Integration связывает согласие
с конкретным Transition.

Без ACS короткое "да"
может быть семантически недостаточным.

Результат:

Модель выдерживает сценарий.


============================================================
20. ГЛАВНОЕ ОБНАРУЖЕННОЕ УТОЧНЕНИЕ
============================================================

Исходная минимальная формула ACS:

ACTIVE CONTENT
+
RESPONSE TARGET

остаётся достаточной.

Но два понятия требуют уточнения.


ACTIVE CONTENT

не должен быть неделимым текстовым blob.

Он должен состоять из адресуемых
смысловых элементов,
если ответ системы содержит
несколько независимо разрешимых смыслов.


RESPONSE TARGET

не обязан быть единственным.

Он должен позволять ссылаться
на один или несколько элементов
или связей Active Content.


Это НЕ означает,
что ACS становится историей разговора.

Он по-прежнему содержит только
активный смысл последнего системного хода.


============================================================
21. УТОЧНЁННАЯ ЛОГИЧЕСКАЯ МОДЕЛЬ ACS
============================================================

ACTIVE CONVERSATION STATE

├── ACTIVE CONTENT
│   └── one or more addressable semantic items
│
└── RESPONSE TARGETS
    └── references to one or more active items / relations


Каждый active semantic item
должен иметь стабильную идентичность
в пределах Active Conversation State,
чтобы пользовательская реакция
могла быть сопоставлена
с конкретной частью предыдущего ответа.


============================================================
22. ИТОГ ПРОВЕРКИ DATA MODEL
============================================================

Проверка не обнаружила необходимости
в новой отдельной персистентной сущности памяти.

Достаточны:

HUMAN MODEL
├── MODEL ITEMS
└── RELATIONS

ACTIVE CONVERSATION STATE
├── ADDRESSABLE ACTIVE CONTENT
└── RESPONSE TARGETS

DIALOGUE HISTORY

+
отдельный HUMAN EXPERIENCE.


Обнаружено одно необходимое уточнение
к ранее сформулированной модели:

RESPONSE TARGET должен поддерживать
множественность,
а ACTIVE CONTENT — адресуемые элементы.


============================================================
23. РЕШЕНИЕ
============================================================

Логическая модель считается
достаточной для перехода
к конкретной технической схеме Data Model.

Перед реализацией необходимо привести
13_Active_Conversation_State.txt
и
16_Discovery_Data_Model.txt

в соответствие с результатом этой проверки:

ACTIVE CONTENT
→ addressable semantic items

RESPONSE TARGET
→ one or more response targets


После этого можно проектировать
конкретные Python / Pydantic структуры.
