DISCOVERY DATA MODEL — SEMANTIC REQUIREMENTS

Статус документа:
Рабочие требования к будущему Data Model Discovery.

Документ переводит утверждённые смысловые контракты
Cognitive Cycle, Human Model, Active Conversation State
и Discovery Memory в требования к структуре данных.

Он НЕ фиксирует окончательную JSON-схему.
Он НЕ фиксирует Python-классы.
Он НЕ фиксирует способ хранения.

Цель документа — определить,
ЧТО будущая структура данных обязана уметь выразить,
до выбора конкретной технической формы.


============================================================
1. ОБЩИЙ ПРИНЦИП
============================================================

Data Model должен обслуживать процесс мышления Discovery,
а не превращать Discovery в заполнение анкеты.

Структура данных должна позволять системе сохранять:

1. накопленное понимание конкретного человека;
2. происхождение этого понимания;
3. степень определённости интерпретации;
4. связи между элементами опыта;
5. отвергнутые и скорректированные версии;
6. незавершённый смысловой контекст последнего хода;
7. буквальную историю разговора отдельно от интегрированной модели.

Data Model не должен требовать,
чтобы заранее известный список полей был заполнен
для продолжения или завершения Discovery.


============================================================
2. ПЕРСИСТЕНТНЫЕ СУЩНОСТИ
============================================================

Минимально между Cognitive Cycles должны сохраняться:

A. HUMAN MODEL

B. ACTIVE CONVERSATION STATE

C. DIALOGUE HISTORY


Human Experience существует отдельно
как профессиональная база знаний
и не является пользовательскими данными.


============================================================
3. HUMAN MODEL: ОСНОВНАЯ ЕДИНИЦА
============================================================

Human Model должен состоять не только
из тематических полей вроде:

problem
motivation
barrier
fear

Такая структура слишком рано навязывает
фиксированную интерпретацию разговора.

Базовая единица Human Model должна уметь представить
ОТДЕЛЬНЫЙ СМЫСЛОВОЙ ЭЛЕМЕНТ пользовательской картины.

Рабочее название:

MODEL ITEM


MODEL ITEM должен как минимум позволять выразить:

CONTENT
— смысл элемента;

KIND
— что это за элемент в текущей рабочей модели;

PROVENANCE
— откуда он появился;

STATUS
— какова его текущая поддержка / определённость;

REFERENCES
— с какими другими элементами он связан,
если такая связь существует.


============================================================
4. CONTENT
============================================================

CONTENT хранит нормализованный смысл,
который должен пережить границу хода.

Примеры:

"раньше любил фотографироваться"

"сейчас почти не хочется фотографироваться"

"старается не снимать футболку перед женой"

"пользователь предполагает, что это связано с возрастом"

"хочет снова спокойно чувствовать себя перед женой"


CONTENT не обязан быть буквальной цитатой.

Буквальная формулировка остаётся в Dialogue History.

При необходимости Data Model должен позволять
связать нормализованный смысл
с исходной репликой пользователя.


============================================================
5. KIND
============================================================

KIND описывает роль элемента
в текущей рабочей картине.

Data Model должен позволять различать
как минимум смысловые типы,
которые уже используются Cognitive Cycle:

- STATED PROBLEM;
- EXPERIENCE;
- LIFE CHANGE;
- BEFORE;
- NOW;
- EMOTION;
- PERSONAL MEANING;
- DESIRED CHANGE / RETURN;
- PREVIOUS ATTEMPT;
- BARRIER;
- USER INTERPRETATION;
- RELATION;
- OTHER PERSON VIEW;
- OTHER RELEVANT USER MATERIAL.

Этот перечень не должен превращаться
в обязательные слоты.

У конкретного пользователя
могут отсутствовать многие типы.

Один разговор может породить
несколько элементов одного типа.


============================================================
6. PROVENANCE
============================================================

Каждый элемент, для которого происхождение
влияет на интерпретацию,
должен сохранять PROVENANCE.

Минимально Data Model должен различать:

USER PROVIDED

USER INTERPRETATION

SYSTEM PROPOSED

OTHER PERSON


SYSTEM PROPOSED недостаточно хранить
как пользовательский факт.

Его текущая реакция пользователя
определяется отдельно через STATUS.


============================================================
7. STATUS
============================================================

STATUS не должен быть только TRUE / FALSE.

Data Model должен позволять выразить как минимум:

SUPPORTED

REJECTED

PARTIALLY SUPPORTED

UNCERTAIN

CORRECTED


Для материала,
который пользователь сообщил напрямую
и который не является проверяемой системной версией,
STATUS не должен искусственно изображать
объективную истинность.

Система хранит пользовательский опыт
как пользовательский материал,
а не как доказанный факт внешнего мира.


============================================================
8. RELATIONS
============================================================

Data Model должен уметь хранить
отношения между MODEL ITEM.

RELATION должна позволять выразить:

SOURCE ITEM / ITEMS

RELATION MEANING

TARGET ITEM / ITEMS

PROVENANCE

STATUS


Примеры смыслов связи:

- BEFORE → NOW;
- пользователь связывает A с B;
- Desired Return относится к Life Change;
- Barrier относится к Previous Attempt;
- несколько изменений образуют одну рабочую картину;
- система предложила связь A ↔ B,
  пользователь её поддержал;
- система предложила связь,
  пользователь её отверг.


Связь должна храниться отдельно от самих элементов,
если её смысл важен для Formulation.

Наличие A и B в Human Model
не означает автоматически,
что между ними существует связь.


============================================================
9. CORRECTION И SUPERSESSION
============================================================

Data Model должен позволять пользователю
исправлять ранее построенное понимание.

Новая коррекция не должна просто добавляться
рядом со старой версией так,
будто обе одинаково актуальны.

Структура должна позволять выразить:

- какой элемент скорректирован;
- какая новая версия его заменяет;
- что старая версия больше не является
  текущей рабочей интерпретацией.

При этом старый материал может оставаться доступным
для объяснимости и истории изменений.


============================================================
10. REJECTED SYSTEM PROPOSALS
============================================================

Data Model должен позволять сохранять
значимые отвергнутые системные версии.

Это необходимо,
чтобы Decision не возвращался
к уже отвергнутому смыслу
только потому, что Human Experience
снова допускает такую гипотезу.

Не требуется хранить бесконечный архив
всех неудачных формулировок.

Хранится смысл отвергнутой версии,
если её повторение способно ухудшить
дальнейшее понимание или диалог.


============================================================
11. INTERPRETATION UNCERTAINTY
============================================================

Неопределённость интерпретации
должна быть представима явно.

Например:

система предложила версию A;

пользователь ответил:

"может быть"

Active Conversation State позволяет понять,
что ответ относится к A.

Но текст не позволяет надёжно определить,
это:

- сомнение;
- частичное согласие;
- внезапное узнавание;
- нейтральное допущение.

Data Model должен позволить сохранить:

A остаётся unresolved / uncertain

без принудительного преобразования
в SUPPORTED или REJECTED.


============================================================
12. ACTIVE CONVERSATION STATE
============================================================

Active Conversation State должен иметь
отдельную структуру от Human Model.

Минимально он должен уметь выразить:

ACTIVE CONTENT

RESPONSE TARGETS


ACTIVE CONTENT должен позволять представить
один или несколько адресуемых смысловых элементов
последнего ответа системы,
которые остаются активными
для следующей реплики пользователя.

Если последний ответ системы содержит
несколько независимо разрешимых смыслов,
Active Content не должен быть
одним неделимым смысловым blob.

Каждый независимо разрешимый active semantic item
должен быть различим внутри ACS.


RESPONSE TARGETS должны позволять ссылаться
на один или несколько элементов,
связей или смысловых вопросов,
которые следующая реплика пользователя
может разрешить или изменить.

Одна пользовательская реплика может независимо:

- подтвердить один target;
- отвергнуть другой;
- скорректировать третий;
- оставить часть targets без ответа.


Если последний ответ системы содержит:

Reflection
+
вопрос о конкретной части Reflection,

Active Content может содержать
несколько адресуемых элементов предъявленной картины,

а Response Targets указывают,
какая конкретная часть или связь
непосредственно вынесена на разрешение.


============================================================
13. ССЫЛКИ И ИДЕНТИЧНОСТЬ
============================================================

Поскольку элементы Human Model
могут связываться, корректироваться,
подтверждаться и отвергаться,
Data Model должен обеспечивать
стабильную идентичность MODEL ITEM.

Конкретная техническая форма
идентификатора пока не определяется.

Но система должна иметь возможность сказать:

- эта связь относится именно к этим элементам;
- эта коррекция заменяет именно эту версию;
- этот Response Target относится именно
  к этой активной версии;
- эта отвергнутая гипотеза уже была проверена.


============================================================
14. DIALOGUE HISTORY
============================================================

Dialogue History хранится отдельно.

Минимально история должна позволять восстановить:

- порядок реплик;
- автора реплики;
- текст реплики.

Будущая реализация может также позволять
MODEL ITEM ссылаться на исходную реплику,
из которой он был получен.

Это повышает объяснимость
и позволяет при необходимости
проверить нормализованную интерпретацию
по исходному тексту.


============================================================
15. ЧТО НЕ ДОЛЖНО БЫТЬ ОСНОВОЙ DATA MODEL
============================================================

Не должны быть центральной архитектурой:

known / unknown

problem = 1.0

motivation = 1.0

pain = 1.0

limitations = 1.0

understanding_score

discovery_complete

required_fields

optional_fields

количество заполненных слотов


Такие значения могут существовать позже
как производная аналитика,
если появится реальная необходимость.

Они не должны определять,
что система понимает человека
или когда Discovery достаточно.


============================================================
16. ПРОИЗВОДНЫЕ СОСТОЯНИЯ
============================================================

FORMULATION

SUFFICIENCY

DECISION

IMPACT

EMOTIONAL ADAPTATION

не обязаны храниться
как отдельные постоянные сущности.

Они могут вычисляться заново
в текущем Cognitive Cycle
из актуальных входов.


------------------------------------------------------------
PRODUCTION DECISION BOUNDARY
------------------------------------------------------------

Production output Decision является SELECTED-ONLY.

Один Cognitive LLM call получает текущее состояние
и возвращает один выбранный DecisionIntent,
соответствующий System Action, Response,
а также необходимые state / reconciliation данные.

После этого deterministic Python State Applier
проверяет и применяет допустимые изменения состояния.

Candidate list, considered possibilities, ranking,
материализованное search space, rationale и chain-of-thought:

- не являются production requirement;
- не входят в persistent Discovery Memory;
- не должны становиться production API/persistent candidate set;
- не нужны State Applier для применения выбранного хода.

Такие структуры допустимы только во внешнем
Conversation Lab / diagnostic tooling.

Лаборатория может сравнивать selected action
с independently frozen challengers
и фиксировать наблюдаемый дефект
MISSED HIGH-VALUE ALTERNATIVE.

Из такого сравнения нельзя выводить,
какие варианты модель латентно рассматривала
или как выглядело её скрытое рассуждение.

Frozen Matched Three-condition Lab на HEAD 7674220
закрыл вопрос о переносе candidate / consideration
materialization в production:

НЕ ПЕРЕНОСИТЬ.


Если часть результата должна пережить ход,
она должна быть преобразована
в соответствующую персистентную информацию:

понимание человека
→ Human Model

незавершённый смысл последнего действия
→ Active Conversation State

буквальный разговор
→ Dialogue History


============================================================
17. МИНИМАЛЬНАЯ ЛОГИЧЕСКАЯ МОДЕЛЬ
============================================================

DISCOVERY MEMORY

├── HUMAN MODEL
│   ├── MODEL ITEMS
│   │   ├── identity
│   │   ├── content
│   │   ├── kind
│   │   ├── provenance
│   │   └── status
│   │
│   └── RELATIONS
│       ├── identity
│       ├── source reference(s)
│       ├── meaning
│       ├── target reference(s)
│       ├── provenance
│       └── status
│
├── ACTIVE CONVERSATION STATE
│   ├── addressable active content
│   └── response targets
│
└── DIALOGUE HISTORY
    └── ordered messages


HUMAN EXPERIENCE
существует отдельно
и не входит в пользовательскую Discovery Memory.


============================================================
18. КРИТЕРИЙ ГОТОВНОСТИ К ТЕХНИЧЕСКОЙ СХЕМЕ
============================================================

Перед созданием конкретных dataclass / Pydantic / JSON
эта логическая модель должна выдерживать
разные типы Discovery-разговоров без необходимости:

- добавлять новый слот под каждый новый жизненный сюжет;
- терять происхождение материала;
- превращать гипотезу в факт;
- терять отвергнутую версию;
- терять пользовательскую коррекцию;
- терять связь между элементами;
- принудительно разрешать неоднозначность;
- дублировать Dialogue History в Human Model;
- дублировать Human Model в Active Conversation State.

Проверка логической модели выполнена
в 17_Discovery_Data_Model_Validation.txt.

По результатам проверки
новая отдельная персистентная сущность памяти
не потребовалась.

Обязательное уточнение,
выявленное проверкой,
внесено в настоящий документ:

ACTIVE CONTENT
→ one or more addressable semantic items

RESPONSE TARGETS
→ one or more references
to active items / relations

После этого уточнения
логическая модель считается достаточной
для перехода к конкретной технической схеме Data Model.


============================================================
КЛЮЧЕВОЙ ПРИНЦИП
============================================================

Будущий Data Model должен моделировать
не список ответов пользователя на вопросы.

Он должен моделировать
элементы рабочей картины человека,
их происхождение,
их текущий статус
и значимые связи между ними.

Техническая схема должна появиться
ПОСЛЕ проверки этой логической модели,
а не определять её заранее.
